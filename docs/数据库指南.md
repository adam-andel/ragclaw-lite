# 数据库构建

Schema 以 `backend/app/models/` 下的 ORM 模型为唯一事实来源，无迁移文件、无版本链。
每次启动执行三个幂等阶段：`create_all` 补建缺失的表 → 幂等 patch 处理加列/删列/改类型
等 `create_all` 做不到的变更 → 漂移检测对比模型与实际库并报告差异。

## 全新安装

删除 `data/sqlite/ragclaw.db` 后启动后端，数据库与种子数据会自动重建。

## 演进 schema

**新增整张表**：改模型后重启即可 —— `create_all` 会自动建表。

**修改已有表**（加列/删列/改类型/加索引/回填）—— 改模型 *并* 在 `app/schema_patches.py` 追加一条 patch：

```python
Patch(
    name="users.avatar_url",
    applied=lambda insp: has_column(insp, "users", "avatar_url"),
    apply=["ALTER TABLE users ADD COLUMN avatar_url TEXT"],
)
```

改模型让全新安装正确，patch 让存量库收敛到同一形状。忘记写 patch，启动时会打出响亮的 `DRIFT DETECTED` 错误并点名缺失的列。

规则：判断条件基于 **live schema 状态**，绝不基于版本号 —— 兄弟栈可能已经应用了不同的 patch 子集。patch **只增不删**；删除一个会破坏任何尚未应用它的数据库。删除类变更要反转谓词（`applied` 表示"目标终态已达成"，所以某列 *消失* 才算应用完毕）。多步操作（如 SQLite 的表重建流程）传 callable 而非 SQL 列表。

多栈从构造上就是安全的：每个栈以任意顺序运行同一组自守卫的 patch，没有共享的版本计数器可冲突。
